# PayU: what we read, and how the plan purchase uses it

Read on 2026-11-04 from PayU's own developer documentation (docs.payu.in). Nothing here was tried against a live PayU account yet; the first real test payment (with the owner's test keys) settles anything marked "to confirm".

## Facts, with where they come from

- **Pages used:** PayU Hosted Checkout ("Web Integration - PayU Hosted", `docs.payu.in/docs/prebuilt-checkout-page-integration`), "Generate Hash for Server-to-Server integration", "Webhook Events and Sample Payloads", and the "Verify Payment API" reference.
- **Where the browser is sent:** the form is POSTed to `https://secure.payu.in/_payment` (live) or `https://test.payu.in/_payment` (test).
- **Required fields:** `key`, `txnid`, `amount` (a string such as `10.00`), `productinfo`, `firstname`, `email`, `phone`, `surl`, `furl`, `hash`. `surl` and `furl` must be https and reachable from the internet. Optional: `curl` (cancel), `udf1` to `udf5`, `lastname`.
- **Request hash:** `sha512(key|txnid|amount|productinfo|firstname|email|udf1|udf2|udf3|udf4|udf5||||||SALT)`, lowercase hex, built on the server. The salt is never sent. Unused udf slots stay as empty strings; the pipes stay.
- **What comes back:** PayU POSTs the customer's browser to `surl` (success) or `furl` (failure) with URL-encoded fields: `mihpayid`, `txnid`, `status` (`success`, `failure`, or `pending` for some bank transfers), `unmappedstatus` (`captured`, `failed`, `userCancelled`), `amount`, `key`, `hash`, `error`, `error_Message`, `email`, `firstname`, `productinfo`, `udf1` to `udf5`, and more.
- **Reply hash (reverse):** `sha512(SALT|status||||||udf5|udf4|udf3|udf2|udf1|email|firstname|productinfo|amount|txnid|key)`. Compare it with the posted `hash`. PayU: "Trust the result only if the hash matches." PayU's pages show four layouts: the plain one; with `additional_charges|` in front; with `splitInfo` right after `status`; and both. We accept a layout only when the reply carries that field, and every layout needs the salt.
- **Limits on what we send (test environment; live is looser):** `firstname` 20 characters, `email` 50, `surl`/`furl`/`curl` 50 and https, `phone` a 10-digit mobile number, `txnid` letters and digits only. PayU's sample replies carry stray spaces in ids, and some ids as numbers.
- **Server-to-server notice (webhook):** set in PayU's dashboard (events Successful, Failed, Refund, Dispute). Success and Failed are form-encoded POSTs with the same fields and a `hash`. Refund and Dispute are JSON with no hash. Retry behaviour and the expected reply are not documented; webhook calls come from fixed PayU IP addresses. PayU calls the webhook "the most reliable way to confirm transaction status" and says not to update an order from the browser return alone.
- **Verify Payment API:** POST `application/x-www-form-urlencoded` to `https://info.payu.in/merchant/postservice.php?form=2` (live) or `https://test.payu.in/merchant/postservice.php?form=2` (test), fields `key`, `command=verify_payment`, `var1=<txnid>` (several joined with `|`), `hash=sha512(key|command|var1|salt)`. The answer has `status` (1 or 0), `msg`, and `transaction_details` keyed by `txnid`, each with `status`, `unmappedstatus`, `amt`, `mihpayid`, `error_code`. A txnid PayU never saw comes back with `status` "Not Found".
- **Test data:** card `5123456789012346`, any future expiry, CVV `123`, OTP `123456` (a failing card is `5123456789012340`); UPI `anything@payu`.

## How we use it (decisions made here, 2026-11-04; the owner may change any)

1. **A payment is believed only when everything agrees:** the reply hash matches (constant-time), the amount, our own order id (`udf1`) and the mode (live or test) match the order we created, and PayU's Verify Payment API, called by our server, says the transaction is `success` with `unmappedstatus` `captured`, at the plain price (no discount, the amounts it reports agree, the debit is not lower). The payment id we keep comes from PayU's answer, never from the posted form. The browser return and the webhook both lead to this one check, so a forged form post cannot switch anything on.
2. **Exactly once.** The order row, then the user row, is locked and the order moves `pending` to `paid` in one database transaction together with the switch-on; a second delivery finds it already `paid` and does nothing. A failure only fills a pending order and never overwrites a paid one; a failed order can still be paid later. One PayU payment id pays one order (unique index).
3. **If PayU cannot be reached, or has not caught up,** the check is asked twice (two seconds apart); then the order stays pending, the webhook answers "try again later" (503), and a daily job checks every unsettled order (newest first, between 10 minutes and 3 days old, only the mode this server is set to). An order PayU has never heard of for more than a day is closed as "never paid at PayU", and can still be paid by a late notice. PayU saying paid at another price is logged as "look at by hand" and changes nothing.
4. **A pass adds to `users.paid_features` and remembers exactly which keys it added** (`users.pass_keys`), so expiry takes away only those and never the owner's manual ticks. Months are added in UTC (31 January plus a month is 28 February). Buying again before the end adds the new term to the end date. The owner's per-creator switch box saves only when the page was loaded from the current state (a payment or another save in between makes it ask for a reload); saving it forgets pass keys the owner has unticked.
5. **Prices stay in `src/lib/pricing.ts`** (since 2026-11-04 per plan, see 15 to 21; an order can be made only for a plan whose prices are set). The early price is counted by creator: another creator's paid early order holds a seat for good (a lapsed holder's seat is not handed on), an unpaid one holds it for two hours; a creator who holds an early pass keeps the early price when renewing, up to 31 days after it ended.
6. **PayU wants a mobile number** (`phone` is mandatory). We do not hold one for creators, so the Buy form asks the creator for it (the owner approved this); it goes to PayU and is not stored on our side.
7. **Limits we accept:** a refund or dispute notice is only logged, the owner handles it by hand; a renewal adds the pass keys again, including one the owner unticked in between; a feature built after someone bought does not reach their running pass; a creator with a running pass is not stopped from closing their account.
8. **To confirm on the first real test payment:** the maximum length of `txnid` (we use 20 letters and digits); whether the browser return reaches `surl` as a form POST; what PayU does when the webhook answers an error (retries?); whether PayU rewrites the `firstname` or `email` it echoes (the hash is built from what it echoes); which of the four hash layouts a normal payment is signed with; whether the Verify Payment API lags its own notice; the database's session time zone (the code does not depend on it, the tests show that).

## Step B decisions (2026-11-04; the owner may change any)

9. **Refunds for a pass (owner's choice, 2026-11-04): fix errors only.** A pass is not refunded once its features are on (not for a change of mind, non-use, a closed or suspended account, or the end of the term). A payment error is put right: a double charge, money taken but features not switched on, a different amount from the price shown, or a fault on our side; where the features simply did not switch on we switch them on for the full term, otherwise the money goes back the way it was paid. Written in the terms (Fees section), the refund policy ("Paid feature passes") and the Buy form's tick box (also checked on the server).
10. **The price shown is the price charged.** The page quotes each term for this creator (early seat or not); the Buy action sends that amount back and the order is made only if it is still the price, so nobody is sent to PayU for a price they did not see (reason `price_changed`). A bad mobile number or email is refused before any order exists, so a typo leaves no unpaid order behind (they count towards the hourly limit and hold an early seat).
11. **What the page says after PayU sends the creator back comes from the database**, never from the `?payment=` word in the address (anyone can type it): a paid order reads as success, a pending one as "waiting for PayU" (the page asks again by itself for about 40 seconds), a failed one as "did not go through". PayU's own error text is never shown (the reply hash does not cover it).
12. **Receipt:** a plain receipt, not a tax invoice, nothing about GST (`docs/rules-check.md` section 2). Only the paying creator can open it; a test payment says it is a test. No receipt email: PayU sends its own payment confirmation, and the receipt is always on the page. If wanted later, it would be one more call after a pass is switched on.
13. **Reminder:** the daily job emails a creator whose pass ends within 5 days, once per end date and plan (`users.starter_reminded_until`, `users.creator_reminded_until`); the row is claimed before sending and given back when the send fails or is off, so tomorrow tries again. The plans page shows the same warning on screen during those 5 days, so it works without email. Email needs `RESEND_API_KEY` and `CONTACT_FROM_EMAIL` on a verified domain.
14. **The mobile number** is typed on our form, posted to PayU and not stored on our side (it is in the privacy policy).

## Plans decisions (2026-11-04; the owner may change any)

15. **Two plans, each its own pass (migration 0056).** Starter and Creator are bought; each order carries its `plan`, and each plan has its own end date on the creator (`users.starter_until`, `users.creator_until`) and its own reminder date. Creator includes everything in Starter, so the features on are the union of the plans running. Nothing is carried from one plan to the other: that is deliberate, because a creator who could turn a long cheap Starter into cheap Creator days would undercut the Creator price, and a downgrade would take away days a creator paid for. The older single pass (0055) is carried over as a Creator pass; `pass_until` and `pass_reminded_until` stay in the table but are no longer read or written.
16. **A plan ending takes away only what nothing running still covers.** `pass_keys` stays the union of what the passes added (never the owner's ticks). When Starter ends while Creator runs, nothing is removed; when Creator ends while Starter runs, only Creator's extra features go; when both end on one run, everything the passes added goes, in one transaction with one audit line.
17. **Refused as pointless: a Starter term a running Creator pass already covers to its end** (`already_covered`, decided at order time with the same month arithmetic as the switch-on). A Starter term that runs past the Creator pass is allowed. Creator over a running Starter is always allowed (it adds features). A reply that pays an older order under the old rules is not a concern: every order carries its own plan and is settled against that plan only, so two unpaid orders of different plans can both be paid in any order without conflict.
18. **Early seats are counted per plan** (`plan = ...` in the seat count and in the renewal check): an early Starter holder renewing Starter keeps the early price; an early Starter does not earn an early Creator.
19. **The custom page and the Pressure meter are not in any pass.** They are sold on request at a price agreed with the creator, and the owner ticks them by hand; a pass ending never removes them (they are never in `pass_keys`). Pinned messages are in none.
20. **Live sales are held shut by `LIVE_SALES_OPEN` (false) in `src/lib/pricing.ts`** while the prices are placeholders: with PayU's live key the Buy action refuses and the page shows no Buy button; with the test key only the owner can buy. The owner opens sales by setting it true together with the final prices.
21. **Accepted limits (added):** an upgrade or downgrade mid-pass is not prorated (each plan simply runs its own term); two plans running at once is possible and harmless; the reminder for a Creator end does not mention that Starter continues.
22. **Accepted limits (from the 2026-11-04 review; none is an exploit):** (a) the early-seat count can overshoot by a seat or two when two creators' early checkouts are paid late in the same minute, because a seat is held by the unpaid order and a late payment is still honoured; (b) a Starter order made before a Creator pass was bought can still be paid after the Creator pass covers it, and then just adds Starter days (the order-time check cannot see the future); (c) a plan's features can last up to the next daily job after its exact end moment, since the job runs once a day; (d) a suspended creator can still be switched on by a payment or by the owner's box, because suspension is about payouts and the tip page, not the features list; (e) the owner's **End now** button changes the plan's end date and features only and never refunds money, and a plan ended that way is bought again like a new one.
23. **The owner ends a plan by hand** from `/admin/creators/<id>` > **Plans bought** (`endCreatorPlan` in `src/app/actions/admin.ts`, `endPlanNow` in `src/lib/plan-orders.ts`): the same switch-off as the daily job runs inside one transaction and writes one audit line, `plan.ended_by_owner`, as the owner with the reason typed.
